# Repository branch and lifecycle reads

`buzz repos branches --id buzz --owner <owner-hex> --json` lists all fetch-authorized hosted branches. Omit `--owner` for your own repository. `--repo-id` and `--repo-owner` are aliases. Without `--json`, output is tab-separated. Each branch has its exact tip, ahead/behind counts against the hosted default branch, `fully_merged`, commit timestamp and optional `open_pr_event_id`.

The relay endpoint is `GET /git/{owner}/{repo}/branches?offset=0&limit=200`. It uses the existing Git fetch access gate and exact URL/method NIP-98 authentication. The response contains `default_branch`, `branches`, `branch_limit`, `branches_total`, `next_offset` and a `snapshot` digest of the default ref and all branch metadata. Pages sort unmerged branches first, then commit time descending, then branch name ascending. The CLI follows pages and rejects changed ref snapshots or incomplete results. PR metadata can change between page requests.

A page inspects at most 200 branches' divergence, with a shared Git concurrency permit, 15-second inspection deadline and 1 MiB per-command output bound. PR association queries are bounded to 10,000 roots and 20,000 statuses; exceeding either returns an error rather than an incomplete answer. An announced empty repository returns an empty list. Missing repositories return 404; denied access preserves the fetch gate's response. Infrastructure failures and timeouts remain errors.

PR associations require an exact `branch-name` match; a shared commit alone does not link unrelated branches. Only current open roots are linked, excluding draft, closed and merged roots. Latest status uses timestamp descending and event ID ascending. Root markers take precedence over reply markers; legacy single `e` tags are accepted. This read recognizes status authors that are the PR author or repository owner. Other role/delegation authority is not inferred.

`buzz repos reconcile --repo-owner <owner-hex> --repo-id buzz [--limit N] [--json] [--apply] [--git-cache <abs-dir>]` returns stable schema-version-2 JSON. JSON is the default. The command joins authorized NIP-34 issue roots, PR roots, PR updates and statuses with hosted branches, then verifies each work item against the exact `main` on the relay and on the GitHub mirror, the mirror pull request for the branch, and GitHub Actions check runs at the exact head. Without `--apply` it writes nothing.

Each work-item row includes issue and PR IDs, authors and status event IDs, the selected PR revision and exact commit, branch and hosted tip, merged-tip flag, mirror PR number, state, head and merge commit, CI state and trusted run count, `in_buzz_main`, `in_mirror_main`, the first-parent `landing_sha` on Buzz main, the `claimed_merge_sha` named by the latest merged status, the proven `merge_sha`, `merge_verified`, `closure_state`, `closure_verified`, `pending_writes` and `blockers`. Multiple explicit issue links produce separate rows. Unlinked issues, PRs and branches remain visible. Titles and prose never establish coverage or closure.

The reducer uses `e` tags marked `issue` for issue links, `E` for same-author PR updates, and same-author PR roots referencing an earlier PR with an unmarked/root `e` tag for supersession. Latest statuses and updates use timestamp descending and event ID ascending. Status authority is conservative: a status counts when one of its identities (its signer, or the principal named by its NIP-OA `auth` tag) is the repository owner or one of the root's identities. Roles are not guessed. The relay does not inspect `auth` tags on status ingest, so the reducer verifies the tag itself through the SDK's NIP-OA check against the event's signer before honoring the principal; an unverifiable tag, or more than one `auth` tag, names nobody. Unrecognized status authority is reported as a blocker.

Backend reads happen after the event reduction. Both mains come from `git ls-remote` (relay through the NIP-98 credential helper, GitHub through `GH_TOKEN` or `GITHUB_TOKEN`), and both are fetched at those exact values into a bare object cache (`--git-cache`, default `~/work/.buzz-reconcile/<owner>-<repo>.git`) so ancestry is answered locally with `git merge-base --is-ancestor`. When the relay has no `/branches` endpoint the branch list is built from `ls-remote refs/heads/*` with `fully_merged` computed against the fetched main; the coverage gap `hosted_refs_reader_unavailable_used_git_ls_remote` says so, and ahead/behind stay zero. The GitHub clone URL comes from the repository announcement; the mirror PR is the same-repository pull whose head branch matches `branch-name` (exact head SHA preferred, then latest updated) after paging every pull to the end. Check runs count only GitHub Actions runs whose `head_sha` is the exact head; `ci_state` is `success`, `failure`, `pending`, `missing`, `not_on_mirror` (GitHub has no such commit) or `not_queried`.

Decision table per row with a commit `C`:

- `merge_verified`: `C` is an ancestor of the relay main and of the mirror main read this run, and the relay main from `ls-remote` equals the hosted default-branch tip. Unread or disagreeing mains verify nothing (`buzz_main_unread`, `mirror_main_unread`, `buzz_refs_snapshot_mismatch`).
- `merge_sha`: the status `merge-commit` when it sits on both mains and contains `C`; otherwise the mirror merge commit under the same test; otherwise `landing_sha`. A named commit that fails the test adds `claimed_merge_not_on_main` or `claimed_merge_does_not_contain_head` (the latter is what a squash or rebase landing looks like; such heads never verify by ancestry), and `mirror_merge_not_on_main` or `mirror_merge_does_not_contain_head` for the mirror's merge commit.
- `closure_verified`: `merge_verified`, the latest PR status is merged and its `merge-commit` passed the containment test, and every linked issue is resolved. `closure_state` is then `verified`.
- `merged_unrecorded`: `merge_verified` but the PR status or a linked issue status is stale; `pending_writes` lists `pr_status:merged` and/or `issue_status:resolved`, and `closure_unrecorded` is a blocker.
- `claimed_unverified`: a merged, resolved or closed claim without `merge_verified`, including closed-unmerged PRs and resolved issues with no PR link.
- `merged_branch_undeleted`: a branch with no PR root whose tip is on both mains. Terminal; there is no status to record, so it never plans a write and never blocks the ledger.
- `active`: everything else.

Blockers are reported independently of `closure_verified`: `mirror_pr_open`, `mirror_head_mismatch`, `missing_mirror_pr`, `ci_failure`, `ci_pending`, `ci_missing`, `ci_not_on_mirror`, `superseded_pr`, `mismatched_head`, `missing_issue_link` and the rest. An orchestrator that wants to fail closed requires `closure_verified` and an empty `blockers` list. The ledger-level `closure_verified` is true only when both mains were read and every merge claim with a commit is verified with nothing unrecorded; `ci_verified` is true when check runs were read for every commit.

`--apply` writes the planned statuses through the same signed builders as `buzz pr status` and `buzz issues status`: a merged PR status carrying `merge-commit = merge_sha`, and a resolved issue status, one write per root. A root is held back, and listed under `skipped` as `blocked_by:<blocker>`, when any of its rows carries `partial_pr_coverage`, `mismatched_head` or `status_precedes_revision`: the record is contradictory and a human decides. It refuses before any write when either main is unread or the hosted tip disagrees with git main, re-reads both mains immediately before writing and aborts if either moved, skips roots the caller may not write (`unauthorized_writer`: the caller is neither repository owner nor root author), and stops at the first rejected write. The `apply` block of the output lists `planned`, `written` (with event IDs and the raw relay response) and `skipped`; in dry-run mode `planned` and `skipped` are populated and nothing else. Idempotency is by construction: only stale statuses are planned, so a second run plans nothing.

`--limit` applies after repository filtering, reduction and verification; `--apply` acts on the full set regardless of `--limit`. `items_total` and `items_truncated` expose display truncation. To support relays that apply coordinate filtering after SQL LIMIT, the command exhausts the authorized event-kind stream using composite cursor pagination before locally filtering repository roots, and reads the repository announcement without a `limit`. Legacy statuses without an `a` tag can therefore be joined by root ID. More than 100,000 events is an explicit read error. This addresses the omission documented in issue `af633f9f6be8c27c2261778c11fe52613583a68a47719148d553b3c8ad9d9fa5`.

Remaining gaps are explicit in `coverage_gaps`: Buzz-native CI run status events are not read (`native_ci_not_queried`), refs and events are separate snapshots, and status authority is limited as above. Terminal CI and merge watchers that run this command automatically are not part of it.
